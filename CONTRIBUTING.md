# Contributing to ExyokiOffice

Thank you for helping improve ExyokiOffice. Contributions may range from a
focused bug fix or documentation correction to a new high-level Office feature.
This guide explains how to make a change that fits the repository and can be
reviewed reliably.

## Before starting

For a small, well-scoped fix, opening a pull request directly is fine. For a
large API, schema, package-format, or compatibility change, open a discussion or
issue first so the design and expected Office behavior can be agreed before a
large implementation is written.

Read these files before changing code:

- [README.md](README.md) for the project overview and supported workflows.
- [AGENTS.md](AGENTS.md) for architecture, repository navigation, and generated
  code boundaries. It is useful to human contributors as well as AI agents.
- [docs/Compatibility.md](docs/Compatibility.md) before making a feature claim.
- The relevant guide under [docs/](docs/README.md) and public header under
  `include/ExyokiOffice/`.

Search existing issues and pull requests before starting substantial work. Keep
one pull request focused on one coherent change.

## Development setup

ExyokiOffice requires C++20 and CMake 3.25 or newer. Use the checked-in CMake
presets so generator options and build directories remain consistent.

### Windows

Visual Studio with the MSVC C++ toolchain is required. The script locates the
newest compatible installation with `vswhere` and initializes its developer
environment:

```powershell
.\WinBuild.ps1 -Configuration Debug -Test
```

Useful variants:

```powershell
.\WinBuild.ps1 -Clean -Configuration Debug -Test
.\WinBuild.ps1 -Configuration RelWithDebInfo -Test
.\WinBuild.ps1 -Sanitizer Address -Configuration Debug -Test
.\WinBuild.ps1 -Configuration RelWithDebInfo -Install
```

### Linux

Use a matching configure, build, and test preset:

```bash
cmake --preset linux-ninja-debug
cmake --build --preset linux-ninja-debug
ctest --preset linux-ninja-debug
```

GCC and Clang presets are available; see `CMakePresets.json` and `README.md`.

Clean builds are relatively slow and memory-heavy because the generated DOM
translation units are large. Reduce the parallel job count when memory is more
limited than CPU capacity.

## Choose the correct implementation layer

Prefer the highest layer that represents the requested behavior:

1. High-level Word, Excel, or PowerPoint editor for user-facing authoring.
2. Typed OpenXML DOM for schema-level element behavior.
3. OPC packaging for parts, relationships, content types, and lifecycle.

Stable public declarations belong under `include/ExyokiOffice/`; their
implementations belong under `sources/`. The `ExyokiOffice::Tools` module
backs reusable package tools, while `tools/exyoki/` should remain a thin CLI
adapter over public library behavior.

Keep vendored dependencies under `sources/pugixml`, `sources/zip`, and
`3rdparty` unchanged unless the contribution explicitly updates or fixes that
dependency.

## Generated code

Do not edit files carrying an `<auto-generated>` banner. In particular, do not
hand-edit the large trees under:

- `include/ExyokiOffice/DOM/`
- `sources/DOM/`

Generated packaging files are listed in `AGENTS.md`. Fix generator behavior in
`gen/` and regenerate through the normal build. Most JSON under `data/` is an
imported metadata snapshot; understand its provenance before changing it.

Generation writes into tracked source directories. After every build or
regeneration, inspect `git status` and `git diff`. Include only deterministic,
intentional generated changes. Output must be identical across supported
standard libraries and compilers; sort data explicitly whenever ordering
affects emitted files.

## Coding style

- Preserve the C++20 baseline.
- Follow `.clang-format` and the repository's `.clang-tidy` configuration.
- Put braces around every control-flow body, including single statements.
- Prefer readable, normally expanded code over compressed expressions or
  one-line functions.
- Use the scalar aliases from `ExyokiOffice/StandardTypes.hpp` in library
  declarations.
- Use a focused private helper class with static methods for file-local helper
  behavior instead of adding an anonymous namespace solely for free helpers.
- Preserve unsupported package content unless the operation explicitly removes
  it. Avoid partial mutation when validation fails.

### Line endings and encoding

Text files are stored and checked out as LF on every platform, including
Windows, and are UTF-8 without a BOM. This is enforced by `.gitattributes`, so
it does not depend on your global `core.autocrlf`; `.editorconfig` carries the
same settings for editors. Neither file needs any local setup — do not override
them per repository.

Two groups are deliberately exempt. Batch files (`*.cmd`, `*.bat`) keep CRLF,
because `cmd.exe` mis-parses multi-line constructs in LF-only files. The
fuzzing inputs under `tests/fuzz/corpus/` and `tests/fuzz/crashes/` are treated
as binary and are never converted, trimmed, or given a final newline: a single
changed byte alters the input and can silently invalidate a crash reproducer.

If a change ever shows a whole file as modified with no visible difference, the
working copy has the wrong line endings. Verify with `git ls-files --eol`: every
text path should read `i/lf w/lf`, apart from the batch files noted above, and
nothing should ever read `i/crlf`. Repair the working tree with:

```powershell
git add --renormalize .
```

Should that stage content changes in `tests/fuzz/`, discard them; those files
must be restored from the index rather than renormalized.

Be careful with non-ASCII characters in C++ sources. The MSVC build does not
pass `/utf-8`, so without a byte order mark MSVC reads a source file in the
system ANSI code page rather than as UTF-8. Comments are unaffected in practice,
but a narrow string literal containing non-ASCII text is re-encoded and no
longer holds the bytes it looks like it holds — and the result depends on the
build machine's locale. Prefer ASCII in literals, or escape the bytes
explicitly, until the build sets `/utf-8`. Do not reintroduce a BOM to work
around this.

On Windows, run the lint script in check mode before submitting:

```powershell
.\WinLint.ps1 -Changed -Check
```

Run the full check when a change affects shared headers or broad infrastructure:

```powershell
.\WinLint.ps1 -Check
```

## Tests

Every behavioral fix should have a focused regression test. Add tests under
`tests/unit/` using the existing doctest conventions. Prefer small in-memory
fixtures or temporary files; do not commit ordinary generated Office documents
or build outputs.

For document behavior, verify the complete relevant path:

1. Create or open the package.
2. Perform the edit.
3. Save it.
4. Reopen it.
5. Assert on the reopened document or package.

This catches relationship, content-type, serialization, and persistence errors
that an in-memory assertion can miss. Runnable examples are registered with
CTest and should also round-trip their output.

For parser or package-input defects, consider whether a fuzz regression belongs
under `tests/fuzz/crashes/<target>/`. Never remove a committed crash input merely
because it now passes.

At minimum, run the affected test target and its matching CTest preset. Run
Debug and RelWithDebInfo when behavior may depend on assertions, optimization,
or configuration. Use AddressSanitizer for memory-safety-sensitive work.

To find out what a layer actually reaches before adding tests to it, measure it:

```powershell
.\WinCoverage.ps1 -Label word
```

`WinCoverage.ps1` builds an instrumented clang-cl tree of its own and writes a
summary table and an HTML report under `build\coverage`. It is a way of finding
untested code, not a gate — no threshold is enforced and nothing in CI runs it.
See [docs/coverage.md](docs/coverage.md).

## Documentation and compatibility

Public behavior is not complete until it is documented. In the same change:

- update the relevant page under `docs/`;
- update `docs/Compatibility.md` when feature coverage changes;
- add new chapters to both `docs/README.md` and `docs/_pdf/chapters.txt`;
- update examples when they are the clearest way to teach the feature;
- update `AGENTS.md`, `llms.txt`, or `llms-full.txt` when navigation,
  architecture, or major workflows change;
- record user-visible changes under `## [Unreleased]` in `CHANGELOG.md`, which
  `RELEASE.md` turns into a release section when the version is cut.

Keep claims precise: distinguish create, edit, preserve, validate, and calculate.
A candid limitation is preferable to an optimistic compatibility statement.

## Commits and pull requests

Write a short imperative commit subject and explain non-obvious design choices
in the body. A pull request should include:

- the problem and intended behavior;
- the implementation approach and important tradeoffs;
- tests and exact commands run;
- compatibility or serialization impact;
- documentation changes;
- intentional generated-file changes, if any;
- any remaining limitation or follow-up work.

Before requesting review, confirm:

- the worktree contains no build outputs, generated example documents, or IDE
  files;
- generated changes are intentional and deterministic;
- formatting, relevant tests, and examples pass;
- installed-package behavior was tested when exports, headers, CMake packaging,
  runtime files, or installation rules changed;
- new public API has clear ownership, failure, and persistence semantics.

## Reporting bugs

Include the operating system, compiler, CMake preset, library version or commit,
minimal reproduction, expected result, and actual result. For malformed Office
packages, reduce and sanitize the document where possible; do not publish files
containing confidential information.

A security vulnerability is not reported this way. Do not open a public issue
or pull request for it; follow [SECURITY.md](SECURITY.md), which describes
private reporting and the boundary between a library vulnerability and an
application's own configuration.
