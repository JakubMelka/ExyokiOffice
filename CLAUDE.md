## Searching and reading

`include/ExyokiOffice/DOM/**`, `sources/DOM/**`, and `data/**` are generated
or imported trees of hundreds of files and tens of megabytes. Reading them
wholesale wastes the context window and rarely points at the layer that needs
changing. Search them by symbol instead of listing them:

```powershell
rg -n "class Paragraph" include/ExyokiOffice/DOM/DocumentFormat/OpenXml/Wordprocessing.hpp
rg -l "SomeOpenXmlType" include/ExyokiOffice/DOM sources/DOM
```

For ordinary repository discovery, exclude the generated, imported, and build
trees:

```powershell
rg --files -g '!include/ExyokiOffice/DOM/**' -g '!sources/DOM/**' -g '!data/**' -g '!build/**' -g '!gen/build/**'
```

## Long-running commands

A clean build takes a long time; a full clang-tidy run takes more than ten
minutes. Give `WinBuild.ps1` and `WinLint.ps1` a tool timeout of at least ten
minutes. If the tool call yields while the process is still running, keep
monitoring the existing process — never start a second build or lint over the
same build tree.

Under a restricted sandbox, the Visual Studio generator can fail during compiler
detection with `MSB4018`, `FileTracker`, and `E_ACCESSDENIED`. The compiler is
present; rerun the same script with sandbox escalation rather than switching
generators or overriding `CMAKE_CXX_COMPILER`.

## Before reporting a change as done

- Build the affected targets and run the relevant CTest layer; report failures
  with their output rather than describing the change as complete.
- After any build, run `git diff` — `generate_openxml` writes into tracked
  source directories, so generated churn can appear without being asked for.
  Keep unrelated regenerated files out of the change.
- Do not edit files carrying the `<auto-generated>` banner; fix `gen/` and
  regenerate.
- Do not commit build products, generated example documents, or IDE-local
  files.
